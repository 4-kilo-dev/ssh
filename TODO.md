# Delivery outcomes

## Stage 1 — Core customer booking path and admin calendar
- [x] Build the customer venue list with list/grid toggle, search, and working mock-data filters for location, date availability, guest capacity, price range, venue type, and amenities; venue detail includes gallery, description, map placeholder, capacity, amenities, packages/pricing, availability calendar, rules/policies, category-grouped suggested vendors, and request-booking action.
- [x] Build booking request form (date, guests, package, notes, summary), confirmation, deposit simulation, success/receipt, failure/retry, and required customer/admin booking views for the core path.
- [x] Booking end-to-end behavior: a customer requests a booking and pays a simulated deposit; the booking appears in Admin as Reserved only when simulated payment succeeds; admin approves it; status becomes Confirmed; venue calendar updates; customer's My Event updates. Shared local state or localStorage keeps all areas in sync.
- [x] Payment outcomes are selected in the demo menu: success, failure, pending. Exact selector label: “Simulation: payment outcome (success / failure / pending)”. A successful outcome alone transitions Requested to Reserved and blocks the date. Pending leaves booking Requested and date unblocked. Failed leaves booking Requested/date unblocked and the customer can retry. Pending and failed copy says “Demo: no real payment is processed” and never implies a real charge or bank action.
- [x] Several customers may send Requested bookings for the same venue/date. When one booking is Reserved or Confirmed, other Requested bookings stay open and are flagged exactly “Needs reschedule or reject”. Keep them flagged until admin explicitly rejects or reschedules them; never change them automatically. Admin calendar shows a conflict warning until each is handled. Rejecting or canceling the Reserved/Confirmed booking releases its date; other overlapping requests are no longer flagged.
- [x] On every payment and receipt screen, persistently show “Demo: no real payment is processed”; label mock receipts “Sample”. Never collect real card or payment credentials.
- [x] Contact details remain masked until the applicable rule is met: venue after deposit; vendor after acceptance or confirmed booking. Admin contact-visibility settings change this behavior.
